# Upstream Sync Log

This file is the per-round decision log for syncing AI Manager with its upstream, CC Switch
(`farion1231/cc-switch`). Each round is audited on a temporary `sync/ccswitch-<upstream-sha>`
branch and every upstream commit in the range is triaged one by one; the newest round is listed
first. The policy itself lives in `docs/adr/0001-upstream-strategy.md` and in the "Upstream sync
discipline" section of `docs/ARCHITECTURE.md`; this file only records the audited range, the
per-commit decision (TAKE, ADAPT, TAKE-FILES, SKIP, DEFER), the product evidence and the open
follow-ups. The tail of the file keeps the capability coverage matrix that measures the product
against the CC Switch baseline.

> Audit date: 2026-09-18  
> Upstream baseline: `upstream/main` `06082e189d65e6d6dbadc35dacdac1ce6c79d89a`
> (2026-09-15, `feat: add MiniMax Code harness support (#7383)`, includes the v3.20.2 / v3.20.3 releases)  
> Product baseline: the initial public commit on `main`. The pre-release branch
> and SHA this audit originally referenced (`feat/spatial-turntable` `95e4ca87`,
> sync branch `sync/ccswitch-06082e18`) belong to the development history that
> was not carried into the public repository, so they no longer resolve here.
> Upstream SHAs still resolve through the `upstream` remote, which is what the
> comparisons below and every future sync actually need.

Compared with the previous round (`db41d701`), `upstream/main` gained 59 commits. The audit only
refreshed the remote refs and compared commit by commit; `upstream/main` was not merged. Backend
fixes were projected onto the existing compatibility layer, proxy data plane and service layer per
ADR-0001, either with `cherry-pick -x` or per file with `git checkout upstream/main -- <path>`;
renderer, README, locale and upstream test commits are never ported.

The unreachable half of the inherited backend has since been deleted: the 30 command modules that
were never registered, `src/deeplink/`, and the WebDAV / S3 sync, quota / balance and managed-OAuth
login services they were the only entry point for. A cherry-pick that touches one of those paths no
longer applies — treat it as SKIP unless the product grows the corresponding feature, in which case
the file comes back from `upstream/main` as a new product-owned module.

## This round: upstream sync audit (db41d701..06082e18)

### Product follow-up: Claude usage import batching (2026-09-20)

`services/session_usage.rs` delegates persistence to `session_usage/claude_batch.rs`:
256-row transactions replace per-record autocommits and pricing lookups are cached
per file. Parsing and proxy/session deduplication stay inherited. The final batch
and cursor commit atomically; a failed batch keeps the old cursor and replay
deduplicates earlier committed rows. Synthetic tests cover multiple batches,
replay, later-batch failure, cursor failure and empty usage. No schema migration
or new dependency. Preserve/adapt this targeted performance and retry fix when
syncing the upstream Claude parser; do not overwrite it with row autocommits.
Current upstream `main` was also checked: its Claude importer already uses a
transaction alongside the newer byte-offset cursor. That cursor still requires
the separately deferred schema migration; this bounded-batch adaptation addresses
the disk-write overhead without silently taking a new schema version.

## Conclusion

AI Manager already covers the core loop for everyday users: tool lifecycle, service connection and
switching, basic Skills / MCP management, lightweight checks, backup and restore, CC Switch import,
and in Advanced Mode local usage / cost, local routing, session browsing and tray quick switch.
Measured against the first-class feature families upstream publishes, AI Manager now covers most
of the common local management paths but is still not a full CC Switch replacement: cloud sync,
Provider OAuth, ordering and encrypted portable archives have not reached the product UI, while
Provider and advanced MCP management remain partial. One-click import by deep link is covered
under ADR-0029. Prompt management is now covered
across every tool in the existing AppType registry.

The product should therefore be positioned as "core flows usable for everyday users", not as
"a complete CC Switch replacement".

## Status vocabulary

- **Covered**: product UI, product API, backend capability and failure recovery are all wired.
- **Partial**: core reads / writes are wired, but common upstream sub-capabilities or product
  requirements still have clear gaps.
- **Not covered**: neither the production UI nor the product API has an entry point; upstream code
  that is still in the tree does not count as product capability.
- **Externally blocked**: the local implementation exists, but going live still needs a product
  account, certificate or public service.

## Current priorities

1. **Unified local extension discovery and explicit adoption (done)**: the first screen discovers
   and merges Skills / MCP across 13 capability scopes, shared Skills are visible to every compatible
   tool, and the user can jump atomically to a specific scope and confirm adoption in all four
   languages; raw config, paths or keys are never sent to the renderer, a partial failure keeps the
   remaining results, and adoption never rewrites live config or the original Skill files. Update
   checks, downloads, pre-replace backups and cross-tool sync for managed Skills reuse the upstream
   services directly; the product only projects known updates and never reports an unreachable
   repository as up to date. Custom source management also reuses the upstream validation and
   repository table; the product accepts only strict GitHub references and deletes by opaque ID,
   exposing no paths, download URLs or credentials; removing a source does not delete already
   installed Skills.
2. **Prompts Basic Management (done across the existing AppType registry)**: create, explicit body
   edit, deletion of non-active items and idempotent import from every tool's native live file are
   in; editing the active item performs a backup, atomic replace, read-back verification and
   rollback on failure. Pi uses its dedicated revision-checked AGENTS.md path instead of a fake
   persisted enable flag.
3. **Common advanced Provider fields (done)**: normal mode adds the model; Advanced Mode adds the
   Base URL in each of the eight tools' native shape and offers write-only Headers only in the
   OpenCode config where upstream really supports them; multi-route per service is chosen only when
   the user explicitly runs a speed test, other raw fields, keys and old Header values never enter
   the renderer, and a failed write restores and re-verifies from the execution snapshot.
   **Provider preset catalog (safe projection done)**: the generator reads the eight upstream preset
   modules tracked in the repository directly; the current projection is 521 API-key safe templates;
   the product drops promotions, referral, regional categories, OAuth / managed accounts, hidden
   entries and incompatible protocols, and public links keep only the HTTPS origin. The renderer
   submits only the stable preset id; the real config is resolved natively and continues through the
   upstream transaction; a sync test demands regeneration and review whenever the upstream catalog
   changes.
   **Universal custom Provider (Advanced safe slice done)**: a separate strict command accepts only
   the name, a write-only API Key, the model and a credential-free HTTPS Base URL without query /
   fragment; native reuses the tool's canonical template and the same create transaction; raw JSON /
   Headers / auth mode are not accepted and no API protocol conversion is claimed. Encrypted portable
   archives still need their own ADR and dependency approval.
4. **Ten-CLI lifecycle and network recovery (done)**: extended registry, updates by real install
   ownership, global automatic network recovery, collapsed process logs, Codex npm corruption repair,
   and pinned-version install / downgrade preserving npm / pnpm / bun / Volta ownership; the Claude
   native install additionally offers a user-confirmed update-channel migration: install first, then
   stage the original launch entry, verify the new entry, and on any failure restore the original
   entry and undo the new install on a best-effort basis. Afterwards the target version must be
   re-probed and matched exactly. Desktop apps are shown as separate read-only status cards and never
   mixed into the CLI update plan; the product's own release storage only hosts AI Manager's own signed updates and never
   mirrors third-party private installers.
5. **Read-only Usage / Cost overview (product slice done)**: reuses the upstream aggregate queries
   and session parsing and exposes only the 30-day aggregate in Advanced Mode; the scan must be
   triggered explicitly by the user, and raw requests, sessions and parse errors never enter the
   renderer. The upstream v3.20.1 byte cursor, tail fingerprint and non-append rewrite detection
   need schema 21 and wait for their own ADR / approval before being synced.
6. **Proxy / failover in Advanced Mode (first safe slice done)**: a small product Domain API wires
   the four tools that already have an upstream data plane; takeover / stop require explicit
   confirmation, the failover queue fails closed, and raw requests, credentials, config backups and
   paths never enter the renderer. Arbitrary listen / circuit-breaker parameters and the other four
   tools remain separate follow-up slices.
7. **Session browsing and tray quick switch (first safe slice done)**: sessions return only
   irreversible references and length-bounded display projections, messages load only after
   selection, and the resume argv is rebuilt in the backend; the tray reuses the product Provider API
   only in Advanced Mode, menus carry no raw Provider IDs, and switching shares the serial lock with
   main-UI writes.
8. **Desktop app status (done)**: ChatGPT / Codex, Claude Desktop, Cursor, ZCode and Cherry Studio
   are probed separately from the CLIs, and the backend re-resolves the fixed system identity before
   opening; the Codex app prompts for an update only after a bounded read of the official update
   metadata strictly compares a higher version, and a failed read stays unknown. When not installed,
   the renderer still sends only the stable App ID and native opens the fixed vendor website. Paths
   and URLs never enter the renderer; no silent downloads, no mirroring of proprietary installers,
   no takeover of vendor updates, and no bypass of explicit regional restrictions.
9. **Provider configuration precedence (done)**: active means only "selected in AI Manager"; the
   eight manageable tools show the actual live config file and the external environment override
   sources. Credential values never cross IPC, safe endpoints are shown only after stripping query /
   fragment, and AI Manager never edits or deletes the user's shell / system variables.
10. **OpenClaw Workspace (first safe slice done)**: the nine fixed files and the journal are operated
    only by fixed ID / date; the first screen is read-only metadata, bodies load on demand and
    bounded, save / delete keep a private recovery copy with verification and rollback on failure,
    and symlinks fail closed.
11. **Cloud sync**: its own Feature covering credentials, conflicts, source verification and
    cross-platform acceptance. Deep-link import shipped separately under ADR-0029.
