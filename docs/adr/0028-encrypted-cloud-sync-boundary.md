# ADR-0028: Cloud Sync Transfers Only Client-Encrypted Immutable Snapshots

- Status: Proposed — awaiting SecretStore, the encrypted archive, and the first transport choice
- Date: 2026-08-29

## Context

Design spec §83 keeps Cloud Sync as a hidden late-stage capability, and roadmap item R5.9 requires an independent
security design. The repository still retains the upstream WebDAV/S3 implementation, but the production API and UI
have been removed; re-exporting those commands directly would bring the plaintext database, Provider keys, remote
credentials, overwrite policy, and paths back inside the product boundary. Editing SQLite on multiple devices at
once or pointing AppData at a sync drive would also cause lock, WAL, and partial-write corruption and cannot be
called cloud sync.

## Proposed Decision

1. The first-phase sync unit is an immutable portable snapshot generated by AI Manager with a versioned manifest;
   the in-use `app.db`, WAL, live tool configuration, logs, caches, recovery copies, and OS SecretStore references
   are not synced.
2. The snapshot is first encrypted locally with the versioned Argon2id + XChaCha20-Poly1305 container of ADR-0030;
   the remote receives only ciphertext, random salt/nonce, format version, ciphertext size, and content hash. File
   names use random IDs and carry no business semantics other than time — no device name, user name, tool, or
   Provider.
3. Cloud credentials go into the ADR-0025 SecretStore and are never written into sync snapshots, SQLite, URLs,
   logs, or the renderer read model. Until SecretStore lands and the encrypted archive is accepted, cloud sync
   cannot enter the production API.
4. The first phase supports only manual "upload new snapshot / list / download to staging / restore after explicit
   preview / delete"; no background two-way merge. Restore reuses the existing backup validation, current-database
   backup, atomic replace, and live sync, and keeps a local rollback point.
5. A conflict is defined as multiple immutable versions coexisting, and the user chooses which one to restore; no
   row-level last-write-wins for Provider/Prompt/Skill. Optimistic concurrency protects only the remote index
   update; on conflict, re-fetch rather than overwrite an unknown version.
6. The recommended first transport is WebDAV over HTTPS only. S3 custom endpoints, path-style, region, temporary
   credentials, and signing clocks expand the configuration and test matrix and should be approved separately
   after WebDAV is verified on real machines. Arbitrary HTTP, URL userinfo, redirects to non-HTTPS/non-original
   hosts, and unbounded response bodies all fail closed.
7. Listing and downloading must have limits on entry count, per-file/total size, timeout, concurrency, and
   decompression; network failures do not modify the local database. Deleting a remote snapshot requires a second
   confirmation and does not mean deleting local data or OS keys.
8. Before production release, at least the following must be completed: two devices, wrong password, tampered
   ciphertext, offline/interrupted upload, duplicate upload, remote concurrency, old formats, missing SecretStore,
   rollback on restore failure, and a credential-log audit.

## Pending Owner Decision

1. Whether to accept "immutable encrypted snapshots + manual restore" instead of real-time/row-level sync;
2. Whether to choose WebDAV as the only launch transport;
3. Whether cloud snapshots may carry Provider keys. Recommended only when the user explicitly chooses "encrypted
   portable snapshot"; ordinary database backups still do not carry them;
4. Remote deletion and retention policy (recommended default: keep the most recent 10; automatic cleanup must be
   enabled separately).

This capability depends on the approval of ADR-0025 and ADR-0030; while the prerequisites are incomplete, the
upstream WebDAV/S3 code may only remain an isolated compatibility layer and must not re-register production
commands.
