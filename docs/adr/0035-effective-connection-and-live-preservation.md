# ADR-0035: Effective Connection Read-Only Model, Per-Tool Precedence Rules, and Settings Preservation on Switch

- Status: Accepted
- Date: 2026-09-07
- Supersedes: ADR-0011 (its decision 1, "never delete or modify user shell variables", is retained)

## Context

ADR-0011 assumed that "the CLI may prefer the external environment", explained it with the same sentence for every tool, and displayed "selected in AI Manager" side by side with an "external overrides" list in a collapsed panel. Real-world testing (2026-09-07) found three problems:

1. Precedence differs per tool, and Claude Code is exactly the opposite: `env` in `settings.json` overrides the shell, and an empty string means cancel. Codex (`CODEX_API_KEY` highest) and Gemini (`.env` only takes effect when the shell has no variable of the same name) are the ones where environment variables win.
2. The probe only read the GUI process environment and grepped seven rc files line by line; files brought in via `source` and `CODEX_API_KEY` were all undetectable, so the panel reported "no external overrides detected" and gave a false sense of security.
3. A CC Switch provider is an entire configuration snapshot, and switching = overwriting the whole file. The user's own hooks / permissions / sandbox / `GOOGLE_CLOUD_PROJECT` vanished on switch; and switching to the official one, which writes `{"env":{}}`, could not override a relay variable in the shell, making the "Use" button a dead letter.

The user's guiding principle (cognitive load first): a non-technical user's first question is "where am I connected right now, and who decided that", not "which entry is selected in AI Manager".

## Decision

1. Domain adds the read-only model `EffectiveConnection { endpoint, endpointSource, credential, credentialSource, providerId, shellInspected }`, returned with `ProviderRuntimeContext`; the source enum is `liveConfig / shellFile / environment / toolDefault`, and the credential is tri-state `configured / toolLogin / missing`. There is no field that could hold plaintext.
2. Evaluation follows each tool's own rules, centralized in the `match ToolId` of `compat/ccswitch/provider_runtime/effective.rs`: Claude file overrides shell (empty string cancels); Codex `CODEX_API_KEY` > `env_key` > `experimental_bearer_token` > `auth.json`; Gemini shell overrides `.env`; Grok / OpenCode recognize only configuration files; OpenCode's in-use provider comes from the `model` field.
3. The terminal environment is evaluated through a login shell: `platform/shell_environment.rs` uses the allowlisted `bash` as a trampoline to run the constant script `exec "$SHELL" -lic /usr/bin/env` (`-lc` for fish, `/bin/sh -c` when `$SHELL` is empty), with an 8-second timeout; on failure it falls back to the process environment and marks `shellInspected=false` in the model, and the UI says so truthfully. rc file line numbers still come from the upstream read-only scanner; if the location cannot be found, only the variable name is reported. Windows uses the process environment (i.e., the registry environment) directly.
4. Presentation: a "Currently in effect" card at the top of the endpoints page (endpoint, source, credential status, and "could not read the terminal environment" when necessary); endpoint cards are tri-state `inUse / overridden / saved`, with `inUse` outlined in the success color plus an "In use" badge and sorted first; the external overrides list in the "see what the CLI actually reads" collapsed section is deleted, keeping only local context and storage (revised 2026-09-08: that collapsed section was moved out of the endpoints page wholesale per ADR-0036 and landed as an always-open panel on the "Local data" page; the endpoints page keeps only the card's own "Open config file" entry). The semantics of `Provider.active` are unchanged (DB selection), used only for constraints such as "cannot remove the current service".
5. The empty placeholder `default` generated by the first-launch import (custom, no endpoint, no key) does not enter the product list; it exists only as a backfill target.
6. The switch write path is wrapped with a preservation layer at the product level: `provider/switching.rs` reads live before switching and, after upstream has written, pastes back everything that does not belong to the **connection keys** (Claude: everything at the top level is preserved except `apiKeyHelper` / `awsAuthRefresh` / `awsCredentialExport` and the `apiFormat` / `api_format` / `openrouterCompatMode` / `openrouter_compat_mode` stripped by the upstream sanitizer; inside `env`, everything except `ANTHROPIC_*`, `CLAUDE_CODE_USE_*`, `CLAUDE_CODE_SKIP_*_AUTH` is preserved; Codex: everything except `model_provider` / `model_providers` / `model` and the MCP projection keys `mcp_servers` / `mcp` is preserved — MCP is owned by the DB, live is only a projection, and upstream re-projects at the end of the switch; Gemini: everything except `GEMINI_API_KEY` / `GOOGLE_API_KEY` / `GOOGLE_GEMINI_BASE_URL` / `GEMINI_MODEL` is preserved). For Claude, if the target does not define `ANTHROPIC_BASE_URL` / `ANTHROPIC_AUTH_TOKEN` / `ANTHROPIC_API_KEY`, `""` is written to disable the shell variable of the same name. Skipped during proxy takeover (placeholder or existing live backup, same judgment as upstream `should_hot_switch`). Upstream `live.rs` has zero changes.
7. Still not done: deleting or modifying user shell variables; OpenCode "Use" writing `model`; resolving `source` chains to locate line numbers.

## Consequences

ADR-0039 supersedes the selection fallback: database state alone no longer means
in use. OpenCode reports default-model and recent-model evidence separately and
reads credential presence from its local auth store. Additive actions are labeled
as adding configuration, not selecting a default model. Configuration read failures
report unknown selection instead of a built-in-provider match.

- Positive: the words "In use" are finally true; the user's own hooks / sandbox / project variables no longer vanish on switch; a relay variable left in the shell no longer turns "switch to official" into a no-op.
- Positive: zero changes to upstream files; the preservation logic and the probe do not fight each other when syncing CC Switch.
- Negative: every time a tool's endpoints page is opened, a login shell is started (about 0.3–2 seconds, longer with heavy rc files); on failure it only degrades and does not error.
- Negative: the upstream keyword table (`get_keywords_for_app` in `services/env_checker.rs`) never matches `CODEX_API_KEY`, `CODEX_ACCESS_TOKEN`, `GOOGLE_API_KEY`, so these variables get no rc file attribution; when the login-shell probe fails they are not detected at all (accepted: upstream is untouched, and the shell's value is what counts).
- Negative: `-lic` runs the user's interactive rc on every probe; background processes started by the rc (ssh-agent, gpg-agent, tmux, etc.) are orphaned in the probe session — the success path does not clean them up; only the timeout path kills the whole process group.
- Negative: non-connection keys such as Codex's `model_reasoning_effort` are preserved across providers; if a relay preset depends on a non-connection key such as `CLAUDE_CODE_MAX_CONTEXT_TOKENS`, that value remains after switching away (the value itself is harmless).
- Negative: DB backfill still stuffs the user's settings into the old provider snapshot (upstream behavior); the product no longer depends on that part of the snapshot, but the snapshot size will include them.
