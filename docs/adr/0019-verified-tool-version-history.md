# ADR-0019: Persist Only Verified Product Tool Version Changes

- Status: Accepted
- Date: 2026-08-28
- Extends: ADR-0010

## Context

ADR-0010 already lets AI Manager install pinned versions while preserving npm, pnpm, bun, Volta, and
other installation ownership, but the tool inventory still holds only the current version and the
publisher's latest version. When a lifecycle task finishes, the product does not know which version
was running before the operation, so it cannot reliably answer "what was the previous version" and
has no local fact for a later one-click rollback to use.

Version history cannot be guessed from periodic scans. Users may upgrade by hand outside AI Manager,
switch PATH, or keep multiple installations; recording such observations as product execution records
would let a later rollback falsely claim it can restore a state the product never managed.
Conversely, writing only when the child process exits successfully is not enough either: past
lifecycle incidents have shown that the default entry point can still be broken or at the wrong
version after a command returns 0.

## Decision

1. Schema v18 adds `tool_version_events`, persisting `tool_id`, `from_version`, `to_version`,
   `source`, `operation_kind`, and the millisecond Unix time `occurred_at`. The auto-increment row ID
   is used only for stable ordering within the same millisecond and does not enter the renderer
   protocol.
2. Only `install`, `update`, and `changeVersion` initiated by AI Manager produce events. Startup scans,
   tool page refreshes, external manual changes, repair, uninstall, and installation-channel migration
   never pose as version-change history.
3. The Application layer reads the current version once before the action starts; after the action
   completes it obtains the target version through the existing `detect + verify` gate. An event is
   appended only when verification succeeds. A failed action, a target version mismatch, or a failed
   post-detection writes nothing.
4. `source` records the installation ownership that post-detection can prove. When npm, pnpm, bun,
   Volta, Homebrew, or the native installer is detected, the corresponding enum is stored; when the
   tool runs but ownership cannot be proven, `unmanaged` is stored, and a rollback-capable package
   manager is never guessed.
5. Writing history is part of the lifecycle success contract. If the tool has changed but the SQLite
   append fails, the task ends with a dedicated "tool verified, history not saved" error and keeps
   actionable guidance; it must not silently claim full success. Running again may produce a
   same-version event, and the "previous version" query skips records where
   `from_version == to_version`.
6. Queries return ordered by `(occurred_at DESC, id DESC)`, at most 100 rows per tool.
   `previousVersion` is derived only from the most recent product event whose `from_version` is
   non-empty and differs from `to_version`; it is an input to later rollback decisions and is not
   copied separately into a second piece of state.
7. The renderer can only query read-only history by stable `ToolId`. Version, source, time, and
   action kind are all generated by the backend; the protocol accepts no SQL, paths, package names,
   commands, or arbitrary query conditions. Version strings undergo length and printable-character
   validation before persistence.

## Consequences

- Every install, update, or pinned-version operation successfully verified by the product has
  auditable before/after versions, and the most recent real previous version can be queried.
- Failed tasks and external PATH changes do not pollute the rollback basis; when the source is
  unknown, later capabilities can still fail closed.
- v17 and earlier databases obtain the empty history table through a standard savepoint migration
  with existing data untouched; the SQL archive exports and restores these non-sensitive events
  together with the database.
- R2.2 must still re-detect the current version and installation ownership before executing a
  rollback, and cannot skip ADR-0010's safety boundary on the strength of history events alone.
